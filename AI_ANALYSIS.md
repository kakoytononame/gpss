# ИИ-анализ результатов моделирования

## Что уже работает

Анализ устроен в два слоя, чтобы приложение оставалось полезным без всякой модели и чтобы модель не придумывала числа.

1. **Встроенный анализатор** (`backend/GpssStudio.Simulation/Queueing/QueueingInsights.cs`). Работает всегда, без сети и без GPU. По описанию СМО, теории и последнему моделированию он выдаёт находки с числами:
   - узкие места (загрузка ≥ 85 %, ≥ 95 % — критично) и сколько каналов нужно для загрузки не выше 80 %;
   - неустойчивые узлы (ρ ≥ 1) и необходимое число каналов;
   - доли отказов, ухода из очереди и отказа от вступления в очередь;
   - расхождение моделирования с точной формулой больше 10 % (обычно слишком короткий прогон);
   - неточные оценки (95 % интервал шире ± 10 %) и во сколько раз удлинить прогон для ± 5 %;
   - класс с наибольшим временем пребывания; приближённые формулы.
2. **Языковая модель** (необязательно) получает эти находки, описание системы и таблицы показателей и пишет пояснение на русском: главное, узкие места, что изменить, насколько доверять результатам. В системной подсказке модели запрещено приводить числа, которых нет в данных.

В интерфейсе: «Конструктор СМО» → «Анализ результатов» → «Проанализировать». API: `GET /api/alina-gpss/studio/analysis/status`, `POST /api/alina-gpss/studio/analysis/queueing` (`{ Model, Run }`). Если модель недоступна, ответ содержит находки и текст ошибки, а не падает.

## Варианты подключения модели

| | Локальная маленькая модель | Большая модель по API (Claude) |
| --- | --- | --- |
| Настройка | `Analysis__Provider=local` | `Analysis__Provider=anthropic` |
| Где работает | на том же компьютере, Docker-профиль `ai` (Ollama) или любой OpenAI-совместимый сервер: llama.cpp server, LM Studio, vLLM | облако Anthropic |
| Модель по умолчанию | задаётся `GPSS_AI_MODEL`, рекомендуется `qwen2.5:3b` (хорошо понимает русский) | `claude-opus-5-5` (меняется в `Analysis__Model`) |
| Ресурсы | 4 потока CPU, 3–4 ГБ ОЗУ, ~2 ГБ диска; ответ 10–40 с на CPU | только интернет |
| Качество пояснений | пересказ находок, иногда неточен в выводах | глубокие объяснения, рекомендации, ответы на вопросы |
| Данные | не покидают компьютер | отправляются в Anthropic (описание модели и показатели, без персональных данных) |
| Стоимость | бесплатно | оплата за токены; один анализ — несколько тысяч токенов |

Рекомендация для учебной среды: начать с встроенного анализатора и локальной модели `qwen2.5:3b` (работает офлайн на ноутбуке), а Claude включать там, где нужны развёрнутые объяснения и есть ключ API.

### Локальная модель (Ollama в Docker)

```bash
GPSS_AI_PROVIDER=local GPSS_AI_MODEL=qwen2.5:3b docker compose --profile ai up -d --build
```

Сервис `ollama-pull` один раз скачивает модель в том `ollama_models`. Можно указать другую модель Ollama (`qwen2.5:1.5b` — быстрее и легче, `qwen2.5:7b` — качественнее, ~8 ГБ ОЗУ). Для своего сервера задайте `GPSS_AI_ENDPOINT` (например, `http://host.docker.internal:8081/v1` для llama.cpp server).

### Claude по API

```bash
GPSS_AI_PROVIDER=anthropic ANTHROPIC_API_KEY=... docker compose up -d --build
```

Вызов идёт через официальный SDK `Anthropic` (`AnthropicLanguageModel`). Включён серверный резерв при отказе модели (`fallbacks: "default"`, бета `server-side-fallback-2026-07-01`): если запрос отклонён фильтрами безопасности, API сам повторяет его на подходящей модели. Его можно убрать в `LanguageModels.cs`.

Настройки (`appsettings.json`, раздел `Analysis`, или переменные `Analysis__*`): `Provider`, `Endpoint`, `Model`, `ApiKey`, `MaxTokens` (2000), `TimeoutSeconds` (120).

## Что можно сделать дальше

1. **Потоковый ответ** (вывод текста по мере генерации): `stream: true` у OpenAI-совместимых серверов и потоковый вызов SDK Anthropic, на фронтенде — `ReadableStream`.
2. **Вопросы к результатам в свободной форме** («что будет, если добавить одну кассу?»): модели передаётся контекст анализа, а для числовых «что если» она вызывает инструменты сервера — пересчёт теории (`/queueing/analyze`) и моделирование (`/queueing/simulate`) с изменённым описанием. Так числа всегда считает движок, а не модель.
3. **Анализ стандартного отчёта GPSS и серий экспериментов**, а не только конструктора СМО: тот же двухслойный подход — правила по таблицам отчёта (загрузка устройств, рост очередей, нестационарность, сравнение половин прогона) и пояснение моделью; для серий — чувствительность показателей к факторам по точкам плана.
4. **Встраивание модели прямо в процесс .NET** без отдельного сервера (LLamaSharp + GGUF-файл). Минус: тяжёлый образ API и долгий старт; отдельный сервис Ollama проще обновлять и отключать.
